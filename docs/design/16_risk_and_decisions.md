# 16. Risks and Decisions

## 주요 결정

### Decision 1. 처음에는 스탠드얼론으로 간다

이유:

- 실시간 멀티플레이는 난이도가 높음
- Vercel 단독으로 WebSocket 서버 운영이 적합하지 않음
- 1차 목표는 감성 체험 완성
- 로컬 저장만으로도 충분한 MVP 가능

### Decision 2. React Three Fiber를 사용한다

이유:

- React/Next.js와 결합이 쉬움
- 컴포넌트 기반으로 구조화 가능
- 바이브 코딩에서 유지보수성이 좋음

### Decision 3. 물리 엔진은 도입하지 않는다

이유:

- 작은 행성 산책에는 단순 구면 이동으로 충분
- 물리 엔진 도입 시 복잡도 증가
- 모바일 성능 관리가 어려워질 수 있음

### Decision 4. primitive geometry로 시작한다

이유:

- 에셋 제작 병목 제거
- 기능 구현을 먼저 검증 가능
- 추후 GLB 교체 구조로 확장 가능

## 리스크

| 리스크 | 설명 | 대응 |
|---|---|---|
| 모바일 성능 저하 | WebGL은 기기별 편차가 큼 | dpr 제한, 단순 geometry |
| SSR 오류 | Three.js는 브라우저 API 의존 | client component/dynamic import |
| 조작감 부족 | 구면 이동이 어색할 수 있음 | 이동 속도/카메라 보간 조정 |
| 원본과 유사성 | 벤치마킹 과정에서 복제 느낌 가능 | 이름/에셋/맵/문구 독립화 |
| 범위 확장 | 멀티플레이 욕심으로 MVP 지연 | 단계별 개발 고수 |
| 에셋 저작권 | 무료 에셋 라이선스 문제 | 직접 제작 또는 라이선스 확인 |

## 구현 중 판단 기준

새 기능을 넣기 전에 다음 질문을 합니다.

1. MVP 핵심 경험에 직접 필요한가?
2. 모바일 성능을 해치지 않는가?
3. Vercel 배포를 복잡하게 만들지 않는가?
4. 원본 사이트와 혼동될 위험이 없는가?
5. 나중에 쉽게 제거하거나 교체할 수 있는가?

## 지금 넣지 말아야 할 것

- 실시간 채팅
- 계정 시스템
- 복잡한 애니메이션 캐릭터
- 대형 지형
- 지도/위성/외부 API
- 인앱 결제
- 관리자 페이지
- 소셜 로그인
- 과한 후처리 효과

## 성공 기준

MVP의 성공은 기능 수가 아니라 다음 경험으로 판단합니다.

- 접속하자마자 작은 세계에 들어온 느낌이 든다.
- 조작을 설명하지 않아도 움직여보고 싶다.
- 메시지를 하나 읽으면 다음 메시지를 찾고 싶다.
- 1분 정도 머물러도 지루하지 않다.
- 모바일에서도 체험이 무너지지 않는다.
